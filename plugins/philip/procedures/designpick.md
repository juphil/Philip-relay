$ARGUMENTS 의 방향을 정하라. **말로 합의하려 들지 말 것** — 후보를 실제 화면으로 만들어 고르게 한다.

**왜 이 커맨드가 있나(실측 근거)**: 색·분위기는 단어로 합의되지 않는다. "새벽 느낌의 어두운 푸른색과 살구색"에 서로 합의했는데도 세 라운드가 어긋난 사례 — 같은 단어를 두고 각자 다른 화면을 떠올린다. 게다가 만든 쪽이 화면을 볼 수 없으면(브라우저 없는 실행 환경) 어긋남을 스스로 발견하지 못한다. 합의는 **함께 본 것**에서만 생긴다.

1. **비교 단위를 정한다.** 한 속성의 효과를 판정하는 라운드는 변수 하나만 움직인다. 전체 방향을 고르는 초기 라운드는 서로 일관된 조합을 비교할 수 있으나, 후보별 차이를 구성 요소로 설명한다.

2. **실물로 만든다.** 후보마다 그 제품의 **실제 콘텐츠가 든 화면**을 렌더한다. 색 견본(스와치)만으로는 면적감이 안 나와 또 어긋난다 — 같은 색도 12px 점으로 쓰면 안 보이고 말풍선 면으로 쓰면 주인공이 된다.

3. **현재 안을 후보에 포함한다.** 보통 후보 1 = 지금 것. 기준점이 없으면 "더 밝게"가 어디서부터인지 서로 다르게 읽는다.

4. **수치를 붙인다.** 후보마다 실제 값(hex·알파·간격·대비비)을 화면에 적는다. 고른 즉시 코드로 옮길 수 있어야 하고, **접근성 미달은 고르기 전에 그 자리에 경고로 표시**한다(고른 뒤 발견하면 다시 골라야 한다).

5. **후보 수는 2~4개다.** 차이가 명확하면 2개, 중간 대안이 필요하면 3개, 탐색 폭이 넓을 때만 4개를 만든다. 같은 화면·같은 크기로 한 장에서 비교한다.

6. **추천 1개 + 근거, 나머지는 왜 아닌지 한 줄.** 옵션만 늘어놓는 것은 판단 유기다(하드 규칙 8).

7. **고른 뒤**: 사용자가 구현까지 승인한 경우에만 코드에 반영한다. 선택만 요청됐으면 결정과 수치만 기록한다.

**보고**: 비교 목적 / 고정한 것 / 움직인 변수 또는 조합 / 후보 2~4개의 수치 / 추천과 근거 / 게시 링크.

**금지**: 화면을 볼 수 없는 환경에서 "아마 이렇게 보일 것"으로 색·간격을 확정하는 것. 볼 수 없으면 계산으로 검증할 수 있는 것(대비비·명도 L*·합성색)까지 하고, **보이는 판정은 사용자에게 넘긴다.**
