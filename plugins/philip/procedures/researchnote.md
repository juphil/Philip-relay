연구노트·현황 보고서·기술 문서를 아래 규칙 전부를 지켜 작성하라. 위반 시 완성 아님.

## 1. 근거 규칙 (제1규칙 — 내용의 자격)
- **실물 확인된 사실만 적는다.** 모든 수치·상태·결과는 코드/문서/실측 기록을 이번에 직접 연 것만. 기억·추측·그럴듯한 수치 금지.
- 확신 없는 수치는 **빼는 것이 정답**(어림값으로 채우지 않는다). 필요하면 실물을 열어 확정 후 기입.
- 상태 표현은 관찰 기준: "완료"는 실측·검증 통과한 것만. 자기선언·"될 것임" 금지.
- 핵심 주장에는 검증 근거를 같은 줄에 병기(예: "5회 반복, 800스텝 전 자릿수 일치"). 결정성·재현성 수치는 자릿수를 자르지 않는다.

## 2. 절차
1. 작성 전 현재 질문과 관련된 프로젝트 기준선·기존 연구 상태·산출물을 실물로 파악한다. `/philip:status`의 선택 회수 원칙을 따른다.
2. 문서 목적과 독자를 먼저 정한다. 사용자에게 목차 승인이 필요한 것은 공식 보고서·대형 문서처럼 구조 선택이 결과를 바꾸는 경우뿐이다. 짧은 연구노트는 바로 작성한다.
3. 관찰, 해석, 가설, 결정, 미확인을 분리한다. 출처가 서로 다른 주장을 한 문장에 합치지 않는다.
4. 본문 작성 후 저장 위치와 확인한 범위를 보고한다.

## 3. 목적별 구조
- **문헌 조사**: 질문 → 검색 범위·제외 기준 → 근거 표 → 합의·충돌 → 결론·불확실성.
- **실험 기록**: 가설 → 기준선·조건 → 결과 → 오류·교란 → 판정 → 다음 실험. CV·DL 수치 실험은 `/philip:exp`·`/philip:judge`를 함께 쓴다.
- **UX 연구**: 사용자·과업 → 방법 → 관찰 → 패턴 → 설계 함의 → 미검증.
- **소프트웨어 R&D**: 문제·제약 → 대안 → 프로토타입·측정 → 위험 → 결정 기록.
- **현황·준비도 보고**: 범위 → 확인된 역량 → 잔여 과제 → 검증 상태 → 다음 결정.

모든 문서에 아키텍처·단기/중기/장기·부록을 강제하지 않는다. 독자의 결정에 필요한 절만 둔다. 산출물과 상세 검증이 많을 때만 부록 포인터로 분리한다.

## 4. 문체
- 프로젝트나 사용자가 정한 문체가 우선이다. 별도 형식이 없으면 짧은 문장과 개조식 목록을 사용한다.
- 작성 과정의 사담은 빼고 독자의 결정에 필요한 근거를 쓴다. 방법·도구·자동화 사용 공개가 정책상 필요하면 숨기지 않는다.
- 사실과 해석이 섞이지 않게 문장을 나눈다. 짧게 쓰기 위해 조건이나 한계를 지우지 않는다.

## 5. 표·리스트 사용 기준
- 비교·매핑·반복 필드가 실제로 더 읽기 쉬울 때 표를 쓴다. 항목 수만으로 표를 강제하지 않는다.
- 인과·맥락 설명은 짧은 문단이나 리스트로 쓴다. 표 셀에 긴 문단을 넣지 않는다.
- 단계·이력은 "단계 | 내용 | 결과" 표로 — 결과 열에 실측치.

## 6. 용어·표기
- **프로젝트가 확정한 호칭을 쓴다** — CLAUDE.md 정체성·메모리의 호칭 재정의가 우선(예: 사용자가 "게임이라 칭하지 말 것"을 확정했으면 플랫폼/시뮬레이터로). 제품·시스템 이름 간 관계(무엇이 무엇에 탑재되는가)를 정확히.
- 언어·기술 용어·식별자 표기는 프로젝트 스타일을 따른다. 낯선 도메인 용어는 첫 등장에 정의한다.
- 번호·기호·인용 형식은 대상 출판물이나 프로젝트 스타일을 따른다.
- 측정 수치는 의미 있는 단위와 조건을 함께 쓴다.

## 7. 파일 규칙
- 위치와 파일명은 프로젝트 문서 관례를 따른다. 기존 문서를 개정할 때는 먼저 읽고, 같은 파일 갱신·새 버전 보존 중 프로젝트의 이력 정책에 맞는 방식을 쓴다.

## 8. 피드백 반영 경계
산출물 피드백은 우선 그 문서와 프로젝트 규칙에 반영한다. Philip Relay 전역 규칙 후보는 여러 프로젝트에 재사용 가능하고 반례 검토를 통과한 경우에만 별도 업데이트 작업으로 제안한다. 피드백 자체는 플러그인 수정·버전 증가·원격 push 권한이 아니다. Philip Relay를 바꾸기로 승인되면 `/philip:updatecheck plugin`의 근거·행동 평가 게이트를 거친다.
